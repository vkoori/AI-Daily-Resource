## این موضوع چیست و چرا الان مهم است؟

وقتی یک تیم مهندسی برای Agentِ خودش یک **Harness** می‌نویسد — یعنی حلقه‌ای
که مدل را فرا می‌خواند، خروجی‌اش را می‌خواند، Tool Call‌ها را اجرا می‌کند و
نتیجه را دوباره به مدل می‌دهد — معمولاً فرضیات زیادی درباره «مدل امروز» در
همان کد Hardcode می‌شود: چه زمانی Context باید Compact شود، مدل چه کارهایی
را نمی‌تواند انجام دهد، Session باید کجا ذخیره شود. مشکل این است که این
فرضیات با هر نسخه جدید مدل منسوخ می‌شوند. Anthropic در این مطلب مهندسی
مثالی می‌زند: یک مکانیزم Reset کردن Context که برای Claude Sonnet 4.5 لازم
بود، با آمدن Claude Opus 4.5 دیگر غیرضروری شد — اما اگر آن منطق در Harness
قفل شده باشد، کسی باید دستی برود و آن را حذف کند.

راه‌حلی که Anthropic برای **Managed Agents** (سرویس میزبانی Agentهای
طولانی‌مدت روی Claude Platform) طراحی کرده، شبیه طراحی یک سیستم‌عامل است:
به‌جای یک «Harness قطعی»، چند **رابط پایدار (Stable Interface)** تعریف شده
که قرار است از عمر هر Harند خاص (even نسخه‌های فعلی خود Anthropic) بیشتر
دوام بیاورند. نویسنده‌های مطلب این رویکرد را «Meta-Harness» می‌نامند.

نکته‌های کلیدی در این معماری:

- **بازیابی پس از خرابی:** چون لاگ Session خارج از Harness نگهداری می‌شود،
  اگر یک Harness از کار بیفتد، یک Harness تازه می‌تواند همان لاگ را بخواند
  و دقیقاً از همان‌جا ادامه دهد — بدون از دست رفتن تاریخچه.
- **مجزاسازی Credential:** توکن‌های Git فقط در زمان راه‌اندازی اولیه
  Sandbox استفاده می‌شوند تا Remote را وصل کنند؛ خودِ Agent هرگز آن‌ها را
  نمی‌بیند. فراخوانی‌های MCP هم از یک Proxy عبور می‌کنند که Credential را از
  یک Vault می‌گیرد — یعنی حتی Harness هم مستقیماً Credential را نمی‌بیند.
- **Context به‌عنوان یک Store، نه یک رشته یک‌طرفه:** به‌جای Compact کردن
  غیرقابل‌برگشت تاریخچه، Harness می‌تواند برش‌های موضعی از لاگ Session را با
  `getEvents()` بخواند و قبل از رساندن به پنجره Context مدل، آن‌ها را
  تبدیل/فیلتر کند.
- **Provisioning تنبل:** Containerها فقط وقتی یک Session واقعاً به آن‌ها
  نیاز دارد ساخته می‌شوند، یعنی فراخوانی مدل می‌تواند پیش از آماده شدن
  Sandbox شروع شود.

## چه زمانی و برای چه کسی کاربرد دارد؟

این مطلب برای هر تیمی که یک Harness سفارشی برای Agent خودش می‌سازد —
به‌خصوص برای وظایف طولانی‌مدت مثل Refactor کردن یک مخزن بزرگ، Workflowهای
چندمرحله‌ای DevOps، یا Agentهایی که باید به VPC یا ابزارهای داخلی شرکت وصل
شوند — ارزش مطالعه دارد، حتی اگر از خودِ سرویس Managed Agents استفاده
نکنید. سه اصل قابل‌انتقال به هر معماری Agent عبارت‌اند از: جدا نگه‌داشتن لاگ
وضعیت از منطق اجرا (برای Debug‌پذیری و بازیابی)، هرگز قرار ندادن Credential
در همان محیطی که کد تولیدشده توسط مدل اجرا می‌شود، و رفتار با Container‌ها
به‌عنوان منابع یک‌بارمصرف و قابل Provisioning بر اساس تقاضا به‌جای
زیرساخت ثابت.
