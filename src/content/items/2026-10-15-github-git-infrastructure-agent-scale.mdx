## همان مسئله، از زاویه دیگر

در همین هفته که Anthropic از بازطراحی کنترل نسخه داخلی‌اش (Scion) نوشت،
GitHub هم مقاله‌ای درباره بازسازی زیرساخت Git خودش منتشر کرد — اما از زاویه
متفاوت: اگر مقاله Anthropic روی سرعت **Checkout** تمرکز داشت، مقاله GitHub
روی گلوگاه **Push** (نوشتن) تمرکز دارد. چرا؟ چون در توسعه Agentic، سرعت کار
یک Agent مستقیماً به این بستگی دارد که چقدر سریع می‌تواند تغییراتش را
Commit و Push کند — و یک Agent، برخلاف انسان، ممکن است ده‌ها بار در ساعت
این کار را تکرار کند.

## نکته مشترک با Scion: فرض‌های Git دیگر برقرار نیستند

<Callout type="analysis">
  این‌که دو شرکت بزرگ (Anthropic و GitHub) تقریباً هم‌زمان و مستقل از هم به
  همین نتیجه برسند — که فرض‌های کلاسیک Git (کلاینت آفلاین، نرخ نوشتن در حد
  انسان) دیگر با واقعیت توسعه Agentic هم‌خوانی ندارد — نشانه‌ای است که این
  یک روند واقعی و گسترده در صنعت است، نه یک مسئله محلی یک شرکت.
</Callout>

برای تیم‌های زیرساخت که Agentهای متعدد به‌طور هم‌زمان به یک مخزن می‌نویسند،
توصیه عملی روشن است: اگر گلوگاه شما «خواندن/Checkout» است، به سراغ راه‌حلی
شبیه Scion (کش محلی محدود + Checkout مجازی) بروید؛ اگر گلوگاه شما
«نوشتن/Push» هم‌زمان توسط چند Agent است، اصل جداسازی ذخیره‌سازی از پردازش
GitHub را الگو قرار دهید — در هر دو حالت، راه‌حل نهایی احتمالاً یک تنظیم
سطحی روی Git موجود نیست، بلکه بازنگری معماری در لایه زیرساخت است.
