## این موضوع چیست و چرا الان مهم است؟

وقتی صحبت از «اجرای یک مدل زبانی» می‌شود، معمولاً تصور یک فراخوانی API ساده
در ذهن است. اما در مقیاس تولید — وقتی هزاران Agent هم‌زمان Context طولانی
می‌خوانند، بین چند Replica پراکنده می‌شوند و الگوی ترافیک‌شان به‌شدت
نوسانی است — مدیریت زیرساخت Inference خودش یک مسئله مهندسی جدی می‌شود.
طبق گزارش llm-d، در بارهای کاری Agentic هزینه نگهداری و بازخوانی Context
گاهی از هزینه خودِ تولید پاسخ هم بیشتر می‌شود.

**llm-d** پاسخ متن‌باز به این مسئله است: یک لایه Inference توزیع‌شده روی
Kubernetes که روی موتورهای اجرای مدل محبوب مثل **vLLM** و **SGLang** کار
می‌کند. این پروژه در سال ۲۰۲۵ توسط Red Hat، IBM، Google Cloud، CoreWeave و
NVIDIA بنیان گذاشته شد و اکنون زیر نظر **بنیاد محاسبات ابری Linux (CNCF)**
اداره می‌شود. نسخه ۱.۰ که در ۲۰ اکتبر ۲۰۲۶ منتشر شد، نخستین نسخه‌ای است که
خودش را «آماده برای مقیاس تولید» معرفی می‌کند.

## چگونه کار می‌کند؟

توانایی‌های پایه‌ای که llm-d پیش از نسخه ۱.۰ هم داشت شامل مسیریابی آگاه از
Prefix-Cache و بار (Load-Aware Routing)، Offload کردن KV Cache، جداسازی
Prefill/Decode، Expert Parallelism گسترده، Inference دسته‌ای/Async، و
پشتیبانی از سخت‌افزار ناهمگون بود. نسخه ۱.۰ این موارد را اضافه می‌کند:

- **کنترل جریان آگاه از اولویت و عدالت** بین Tenantهای مختلف روی یک Fleet
  مشترک.
- **دسترس‌پذیری بالا برای Router** با Standby فعال و امکان به‌روزرسانی
  Rolling بدون قطعی.
- **مدیریت هماهنگ Replicaهای Prefill/Decode.**
- **یک API پیکربندی نسخه ۱** برای استانداردسازی تنظیمات.
- **مسیریابی آگاه از Session، زمان‌بندی مبتنی بر اولویت نوبت، و پشتیبانی از
  وضعیت Responses API** — مشخصاً برای الگوهای Agent طراحی شده‌اند.

به‌عنوان یک نمونه موردی، IBM Research گزارش داده در یک پروژه تصحیح خطای
کوانتومی، استفاده از llm-d هزینه Inference را ۱۱.۵ برابر کمتر از یک راه‌حل
کاملاً اختصاصی (Proprietary) کرده، با نرخ برخورد Prefix-Cache حدود ۹۸٪ و
هزینه ترکیبی حدود ۰.۱۱ دلار به ازای هر میلیون توکن. در یک دمو با مدل GLM
5.2 (حدود ۷۵۳ میلیارد پارامتر)، llm-d توانسته در اوج بار، ۶.۶ میلیون توکن
خروجی در دقیقه و تا ۳۰۰۰ Agent کدنویسی هم‌زمان را بدون هیچ Preemption پردازش
کند.

## چه زمانی و برای چه کسی کاربرد دارد؟

llm-d برای تیم‌هایی که مدل‌های خودمیزبانی‌شده (Self-Hosted) را روی
Kubernetes در مقیاس بزرگ اجرا می‌کنند — به‌خصوص برای Workloadهای Agentic با
Context طولانی و تعداد بالای درخواست هم‌زمان — گزینه‌ای است که ارزش بررسی
دارد، مخصوصاً چون روی vLLM و SGLang که از قبل محبوب‌اند کار می‌کند و از
طریق GKE یا CoreWeave Kubernetes Service هم در دسترس است. برای تیم‌هایی که
صرفاً از API‌های مدل‌های بسته (مثل Claude یا GPT) استفاده می‌کنند و خودشان
زیرساخت Inference را مدیریت نمی‌کنند، این پروژه مستقیماً کاربردی ندارد، اما
شناخت آن برای درک اینکه چرا قیمت API ارائه‌دهندگان مختلف این‌قدر متفاوت
است، مفید است.

<Callout type="fact" title="نکته‌ای که به‌صورت مستقل تأیید می‌شود">

  سازگاری آن با vLLM و SGLang، از طریق گزارش‌های مستقل CNCF و رسانه‌های فنی

  اعداد عملکردی که صرفاً از شرکت‌های بنیان‌گذار نقل شده‌اند.
</Callout>
