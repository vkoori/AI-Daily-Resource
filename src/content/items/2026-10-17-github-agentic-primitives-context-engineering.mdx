## این موضوع چیست و چرا هنوز مهم است؟

با رایج‌شدن دستیارهای کدنویسی Agentic، بسیاری از تیم‌ها کار را با یک پیام
گفتگویی به مدل شروع می‌کنند: «این باگ را درست کن»، «این ویژگی را اضافه کن».
این روش برای کارهای کوچک و یک‌باره خوب کار می‌کند، اما وقتی وظیفه بزرگ‌تر
می‌شود یا چند نفر باید همان الگو را تکرار کنند، نتیجه غیرقابل‌پیش‌بینی و
وابسته به مهارت Prompt‌نویسی فرد می‌شود. این مقالهٔ مرجع GitHub (که با وجود
گذشت حدود یک سال از انتشارش، همچنان یکی از کامل‌ترین چارچوب‌های عمومی برای
«مهندسی‌کردن» این فرایند است) یک راه‌حل سه‌لایه پیشنهاد می‌دهد تا تجربه و
تخصص انباشته در Prompt‌ها را به دارایی قابل‌استفادهٔ مجدد تیم تبدیل کند.

## مشکل: Prompt خوب، به‌تنهایی مقیاس‌پذیر نیست

مشکلی که مقاله به آن می‌پردازد ساده است: حتی یک Prompt خیلی خوب، وقتی فقط در
ذهن یا تاریخچهٔ چت یک نفر زندگی کند، قابل‌اشتراک، قابل‌بازبینی (Code Review)
یا قابل‌اجرا در CI/CD نیست. راه‌حل مقاله، بیرون‌کشیدن این دانش از گفتگوهای
پراکنده و نوشتن آن به‌صورت فایل‌های Markdown ساختاریافته و قابل Commit‌شدن
در مخزن کد است.

## Inner Loop در برابر Outer Loop

مقاله بین کار تعاملی («Inner Loop» — VS Code و Copilot برای کار لحظه‌به‌لحظه)
و اجرای تکرارپذیر («Outer Loop» — ابزارهایی مثل GitHub Copilot CLI یا OpenAI
Codex CLI برای CI/CD و محیط Production) تمایز می‌گذارد، و یک مثال واقعی از
Workflow در GitHub Actions ارائه می‌دهد که روی هر Pull Request، اسکریپت
بازبینی امنیتی را با چند Runtime مختلف اجرا می‌کند.

<Callout type="analysis">
  مقاله از ابزاری به‌نام APM («Agent Package Manager» — شبیه npm برای
  Primitiveها) به‌عنوان بخشی از راه‌حل یاد می‌کند، اما این ابزار پروژهٔ شخصی
  خودِ نویسنده است که روی حساب گیت‌هاب شخصی او میزبانی می‌شود — نه یک ابزار
  رسمی GitHub، و مقاله این نکته را به‌روشنی مشخص نمی‌کند. همچنین ادعاهایی مثل
  «این چارچوب، AI را قابل‌اعتماد و قابل‌پیش‌بینی می‌کند»، «آمادهٔ Production با
  قابلیت‌اطمینان Enterprise» یا «همیشه بهتر است Context Window تازه داشته
  باشید» بدون هیچ آزمون یا عدد مشخصی ارائه شده‌اند — این‌ها توصیهٔ معقول
  نویسنده‌اند، نه یافتهٔ اندازه‌گیری‌شده.
</Callout>

## چرا هنوز ارزش خواندن دارد

<Callout type="tip">
  اگر تیم شما هنوز هر Prompt را از صفر در گفتگو می‌نویسد، نقطهٔ شروع خوب طبق
  این چارچوب این است: اول یک یا دو فایل `.instructions.md` برای قراردادهای
  تکرارشوندهٔ کدبیس بنویسید، بعد یک `.chatmode.md` برای محدودکردن دسترسی ابزار
  در نقش‌های حساس، و در آخر یک `.prompt.md` با دروازهٔ تایید برای Workflowهای
  پرریسک‌تر. نیازی نیست همهٔ شش نوع فایل را یک‌جا بسازید.
</Callout>
