## چرا Git در Anthropic به گلوگاه تبدیل شد

Git حدود دو دهه پیش برای یک فرض بنیادی طراحی شد: کلاینت (توسعه‌دهنده) اغلب
آفلاین است، پس باید کل تاریخچه مخزن را به‌صورت محلی کپی کند. این فرض برای
یک توسعه‌دهنده انسانی که روزی چند بار Commit می‌کند منطقی بود. اما با رشد
استفاده از Claude Code در Anthropic، مصرف‌کننده اصلی مونوریپو دیگر انسان
نبود — بلکه صدها Agent و Job خودکار بودند که هرکدام می‌توانستند در عرض چند
دقیقه چندین Commit و Merge انجام دهند.

نتیجه عملی: Clone و Checkout کردن مونوریپو، که زمانی چند دقیقه طول می‌کشید،
به گلوگاه اصلی سرعت توسعه با کمک Agent تبدیل شد؛ هر Agent قبل از شروع کار
واقعی، باید منتظر می‌ماند تا یک کپی سنگین از کل تاریخچه را دریافت کند.

## راه‌حل: Scion — فرض «سرور همیشه در دسترس است»

تیم زیرساخت Anthropic به‌جای وصله‌زدن Git، یک سیستم کنترل نسخه داخلی به‌نام
Scion ساخت که دقیقاً فرض برعکس دارد: کلاینت (چه انسان، چه Agent) تقریباً
همیشه به سرور متصل است، پس نیازی نیست همه‌چیز محلی کپی شود.

<Callout type="analysis">
  این یک تصمیم معماری آگاهانه و قابل‌بحث است، نه یک واقعیت جهانی: Anthropic
  می‌پذیرد که اتصال دائم به سرور را فرض گرفته، که برای توسعه کاملاً آفلاین
  (مثلاً در پرواز یا شبکه ضعیف) مناسب نیست. خودِ این مقاله تأکید می‌کند Scion
  جایگزین عمومی Git نیست.
</Callout>

سه تغییر اصلی که این فرض را عملی می‌کند:

1. **پردازش تاریخچه روی سرور** — عملیات سنگین مثل `blame` و محاسبه Merge
   دیگر روی ماشین کلاینت اجرا نمی‌شود؛ سرور آن‌ها را انجام می‌دهد و فقط
   نتیجه را برمی‌گرداند.
2. **کش محدود سمت کلاینت** — به‌جای کپی کامل تاریخچه، کلاینت فقط یک کش کوچک
   و تازه از آنچه واقعاً لازم دارد نگه می‌دارد.
3. **Checkout کم‌حجم و مجازی‌سازی‌شده (Sparse/Virtualized)** — یک Job یا
   Agent که فقط باید سه فایل را بخواند، مجبور نیست کل مونوریپو را روی دیسک
   بیاورد؛ فقط همان فایل‌های لازم به‌صورت مجازی در دسترس قرار می‌گیرند.

## درس برای تیم‌های دیگر

<Callout type="tip">
  اگر مصرف‌کننده اصلی مخزن کد شما دیگر عمدتاً انسان نیست بلکه Agentها و
  Pipelineهای خودکارند، فرض‌های کلاسیک ابزار کنترل نسخه (مثل «کلاینت باید
  همه‌چیز را محلی داشته باشد») را دوباره بررسی کنید. لازم نیست حتماً Git را
  کنار بگذارید — اما سرعت Checkout و Merge را به‌عنوان یک معیار جدی
  زیرساختی، نه یک مزاحمت جزئی، اندازه‌گیری کنید. این الگو را GitHub هم
  هم‌زمان و از زاویه‌ای متفاوت (مقیاس Push، نه مقیاس Checkout) گزارش داده،
  که نشان می‌دهد این یک روند صنعتی گسترده‌تر است، نه یک تجربه ایزوله.
</Callout>
