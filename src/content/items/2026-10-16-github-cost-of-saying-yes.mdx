## این موضوع چیست و چرا الان مطرح شده؟

نویسنده مثالی می‌زند: درخواستی برای نشان‌دادن یک فیلد `last_active_at` که
از قبل در Backend وجود دارد، ۴۰ دقیقه بحث می‌خواهد و در نهایت با تخمین
کم‌اطمینان «یک یا دو روز» تمام می‌شود — بدون اینکه کسی واقعاً تلاش کرده
باشد آن را بسازد. استدلال اصلی مقاله این است: زمانی که نوشتن نسخهٔ اول یک
قابلیت گران بود، احتیاط تیم‌ها قبل از شروع منطقی بود. اما حالا که یک Agent
می‌تواند در چند دقیقه یک Patch اول بسازد، خودِ مذاکرهٔ «آیا این در محدودهٔ
کار ماست؟» می‌تواند گران‌تر از ساختن آن تغییر باشد.

<Callout type="fact">
  این یک یادداشت شخصی و تجربه‌محور از یک مهندس در تیم Copilot Agent Control
  Plane در GitHub است، نه یک مطالعهٔ آماری؛ نویسنده هیچ عدد یا داده کمّی
  ارائه نمی‌دهد و مثال `last_active_at` را به‌عنوان یک الگوی مشاهده‌شده
  (نه یک مورد مستندشده) معرفی می‌کند.
</Callout>

<Callout type="analysis">
  چارچوب نویسنده و دسته‌بندی‌های او (مثل نمونه‌های «ارزان» در برابر «نه‌ارزان»،
  و فهرست سؤالات بازبینی) برداشت و توصیهٔ شخصی اوست، نه یک استاندارد رسمی
  GitHub. با این حال، چون از داخل تیمی می‌آید که مستقیماً روی زیرساخت Agentهای
  کدنویسی GitHub کار می‌کند، به‌عنوان یک نمونهٔ باتجربه از مواجهه با این
  مسئلهٔ رایج ارزش دارد.
</Callout>

## چه زمانی باید مرز قاطع بگذاریم؟

<Callout type="caution">
  نویسنده تأکید می‌کند که این چارچوب برای تغییرات کوچک و قابل‌برگشت است، نه
  برای همه‌چیز. برای تغییراتی که رفتار Authorization، حفظ/حذف داده
  (Data Retention)، حریم خصوصی، صورتحساب یا قرارداد عمومی API را دست می‌زنند،
  حتی اگر دیفِ تولیدشده توسط AI کوچک و تمیز به‌نظر برسد، باید همچنان قبل از
  هر تلاشی به‌صورت دستی و با احتیاط کامل بررسی و تصمیم‌گیری شود.
</Callout>

<Callout type="tip">
  نکتهٔ عملی برای تیم‌های کوچک: دفعهٔ بعد که بحث «آیا این تغییر کوچک ارزش
  انجام‌دادن دارد؟» بیش از چند دقیقه طول کشید، به‌جای ادامهٔ بحث، از یک
  Agent کدنویسی بخواهید محدودیت‌های روشن (Feature Flag، بدون تغییر API
  عمومی، با تست) را رعایت کند و یک Patch بسازد؛ دیفِ واقعی معمولاً سریع‌تر
  از بحث نظری، مشخص می‌کند که آیا کار واقعاً کوچک بوده یا نه.
</Callout>
