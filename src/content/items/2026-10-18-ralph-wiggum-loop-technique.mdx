## این تکنیک چیست و چرا الان دوباره مطرح شده؟

Ralph (با نام کامل‌تر «Ralph Wiggum Loop»، به نام شخصیت کارتونی Simpsons)
نام تکنیکی است که Geoffrey Huntley برای اولین بار در مِی ۲۰۲۵ معرفی کرد:
یک حلقه bash ساده که همان یک Prompt ثابت را بار‌ها و بار‌ها به یک Agent
کدنویسی (مثل Claude Code) می‌دهد تا وقتی که شرط پایان مشخص‌شده برآورده
شود. این ایده در اوایل ۲۰۲۶ دوباره مورد توجه قرار گرفت — هم به‌خاطر پوشش
خبرنامه‌هایی مثل The Pragmatic Engineer («Ralph Mania»، ژانویه ۲۰۲۶) و هم
چون Anthropic یک Plugin رسمی برای Claude Code بر همین اساس منتشر کرد.

به‌طور پیوسته روی یک Spec کار می‌کند تا کدبیس به‌مرور به سمت آن Spec حرکت

## چه چیزی واقعیت است و چه چیزی تحلیل/هشدار است

<Callout type="caution" title="ریسک‌ها و محدودیت‌ها (نقل از منابع متعدد)">
  این روش فقط برای کارهایی مناسب است که نتیجه‌شان با ابزار خودکار (تست،
  Lint، بررسی ساختار فایل) قابل تأیید باشد — نه برای کاری که به قضاوت درباره
  تجربه کاربری یا منطق کسب‌وکار مبهم نیاز دارد. اجراهای طولانی و خودمختار
  نگرانی‌های واقعی درباره اعتماد، قابلیت بازبینی، و اعتبارسنجی Diffهای بزرگ
  بدون نقطه توقف انسانی ایجاد می‌کنند؛ Compaction می‌تواند باعث انحراف از
  هدف اصلی شود درحالی‌که به‌ظاهر پیشرفت ادامه دارد؛ و بدون محدودیت صریح،
  یک اجرا می‌تواند مقدار زیادی توکن مصرف کند. خودِ Huntley هم هشدار داده که
  Plugin رسمی می‌تواند اشتباهاً به‌عنوان یک محصول «کاملاً بدون نظارت» برداشت
  شود، درحالی‌که همچنان به نظارت نیاز دارد.
</Callout>

<Callout type="analysis" title="ارزیابی Thoughtworks (رتبه Assess، نه Adopt)">
  Thoughtworks این تکنیک را «ارزش بررسی برای فهمیدن تأثیرش روی سازمان شما»
  توصیف می‌کند — یک رتبه محتاطانه، نه توصیه برای استفاده گسترده فوری
  (Adopt) و نه هشدار برای پرهیز (Hold). نکته جالب: Thoughtworks رویکرد
  مرتبط «تیم Agentهای کدنویس» را هم Assess رتبه‌بندی کرده، اما «Swarm
  Agentهای کدنویس» را با رتبه هشدارآمیزتر «Caution» علامت زده — بدون این‌که
  دلیل دقیق این تفاوت را توضیح دهد.
</Callout>

## چرا برای تیم‌های مهندسی نرم‌افزار اهمیت دارد

Ralph Loop نمونه خوبی از یک ایده بسیار ساده (یک حلقه bash) است که با انتخاب
درست نوع کار، می‌تواند بخش قابل‌توجهی از کارهای تکراری و مکانیکی مهندسی
نرم‌افزار را بدون نظارت لحظه‌به‌لحظه جلو ببرد — اما خط قرمز آن هم روشن است:
هر وظیفه‌ای که معیار اتمامش به قضاوت انسانی نیاز داشته باشد، کاندید خوبی
برای این روش نیست، و رهاکردن یک اجرای طولانی بدون سقف و بدون بازبینی،
دقیقاً همان ریسکی است که هم Huntley و هم Thoughtworks به آن اشاره می‌کنند.
