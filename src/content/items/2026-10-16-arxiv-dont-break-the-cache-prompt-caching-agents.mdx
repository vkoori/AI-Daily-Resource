## این موضوع چیست و چه مشکلی را حل می‌کند؟

وقتی یک Agent چند بار پشت‌سرهم مدل را صدا می‌زند (مثلاً برای جست‌وجوی وب،
خواندن نتیجه، و تصمیم‌گیری دربارهٔ قدم بعدی)، حجم Context هر بار بزرگ‌تر
می‌شود و هزینه و تأخیر به‌سرعت بالا می‌رود. ارائه‌دهندگان بزرگ (OpenAI،
Anthropic، Google) قابلیت Prompt Caching ارائه می‌دهند تا بخش‌های تکراری
Prompt دوباره پردازش نشوند، اما تا این پژوهش، هیچ بررسی کمّی مشخصی نشان
نمی‌داد این صرفه‌جویی در عمل، برای Workloadهای Agentic واقعی، چقدر است و
کدام راهبرد Caching بهتر عمل می‌کند.

<Callout type="fact">
  روش پژوهش: بیش از ۵۰۰ نشست Agent با System Promptهای حدود ۱۰ هزار توکنی
  روی DeepResearch Bench (Agentهایی که جست‌وجوی وب واقعی انجام می‌دهند)،
  با Ablation روی اندازهٔ Prompt از ۵۰۰ تا ۵۰ هزار توکن و ۳ تا ۵۰
  فراخوانی ابزار در هر نشست.
</Callout>

<Callout type="tip">
  پیشنهادهای عملی پژوهش برای تیم‌هایی که Agent می‌سازند:
  محتوای ثابت (دستورالعمل‌ها، تعریف ابزارها) را در ابتدای Prompt نگه دارید
  و محتوای دینامیک را در انتها بگذارید؛ در میانهٔ یک نشست، تعریف ابزارها را
  تغییر ندهید (این کار Cache را می‌شکند)؛ نتایج متغیر و ناپایدار ابزارها
  را هرگز داخل بلوک Cache قرار ندهید؛ و پیش از تکیه بر Caching، مطمئن شوید
  Promptتان از حداقل اندازهٔ قابل‌کش هر ارائه‌دهنده بزرگ‌تر است.
</Callout>

<Callout type="analysis">
  نتایج بین سه ارائه‌دهنده متفاوت بود، یعنی نمی‌توان یک راهبرد واحد را بدون
  تست روی هر پلتفرم به‌کار برد — پیشنهاد نویسندگان این است که پیش از اتکا
  به Full-Context Caching به‌عنوان «بهترین گزینه»، آن را روی Workload و
  ارائه‌دهندهٔ خودتان Benchmark کنید.
</Callout>
