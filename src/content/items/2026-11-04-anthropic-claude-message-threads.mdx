## این موضوع چیست و چرا الان مطرح شده؟

در معماری معمول Agentهای مبتنی بر Claude API — مثل Claude Code یا یک
Agent با Computer Use — هر نوبت گفت‌وگو باید کل تاریخچهٔ مکالمه (پیام‌های
قبلی، System Prompt، تعریف Toolها) را دوباره در درخواست HTTP ارسال کند،
چون API به‌طور پیش‌فرض Stateless است. در مکالمات طولانی (مثلاً Agentی که
صدها هزار توکن کانتکست دارد)، همین ارسال و اعتبارسنجی مجدد حجم بزرگ داده
در هر نوبت، بخشی قابل‌توجه از تأخیر کلی را تشکیل می‌دهد — جدا از زمان
خودِ Inference مدل. Anthropic در ۲ نوامبر ۲۰۲۶ ویژگی Message Threads را
در Beta عمومی منتشر کرد تا دقیقاً همین بخش از تأخیر را حذف کند.

  فهرست، خوانش یا حذف دستی Threadها وجود ندارد. Threads از Message
  Batches، Token Counting، Compaction درخواستی و بیشتر قابلیت‌های
  Context Editing پشتیبانی نمی‌کند و برای سازمان‌هایی با Inference
  Hooks فعال، یا نیاز به Zero Data Retention/HIPAA، در دسترس نیست.

## چه زمانی و برای چه کسی کاربرد دارد؟

این قابلیت دقیقاً برای Agentهای بلندمدت طراحی شده: Coding Agentها
(مثل Claude Code)، Agentهای Computer-Use، و هر Workflowای که مکالمه را
در طول صدها هزار توکن کانتکست ادامه می‌دهد. چون مصرف توکن تغییر
نمی‌کند، سود اصلی صرفاً کاهش تأخیر ادراک‌شده توسط کاربر/Agent است، نه
کاهش هزینه. Threads به‌صورت پیش‌فرض برای بیشتر کاربران Claude Code فعال
شده و روی پلتفرم بومی Claude، AWS، Microsoft Foundry و Google Cloud (در
دسترس است؛ تیم‌هایی که از Zero Data Retention یا HIPAA استفاده می‌کنند
نمی‌توانند از آن بهره ببرند و باید منتظر گسترش دسترسی بمانند.

## مقایسه با گزینه‌های مشابه

این الگو از نظر مفهومی به Context Caching سمت سرور در سایر پلتفرم‌ها
(مثل Context Caching در Gemini یا Prompt Caching خودِ Anthropic) شبیه
است، اما هدفش متفاوت است: Prompt Caching هزینه و توکن را کاهش می‌دهد،
در حالی که Threads صرفاً از ارسال مجدد دادهٔ تکراری در شبکه و
Tokenization مجدد آن جلوگیری می‌کند — هزینهٔ توکن کلود دست‌نخورده
می‌ماند. برای بهترین نتیجه، این دو تکنیک مکمل هم‌اند: Threads برای
کاهش سربار شبکه/درخواست، و Cache Breakpointهای دستی درون همان Thread
برای کاهش هزینهٔ واقعی توکن.
