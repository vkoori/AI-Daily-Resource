## چرا طراحی Tool با طراحی API فرق دارد؟

وقتی برای یک انسان یا یک سرویس دیگر API می‌نویسیم، معمولاً کامل‌بودن و
دقت تکنیکی مهم‌ترین معیارند. اما یک Agent، Context محدود دارد: هر فیلد
اضافه، هر شناسهٔ فنی بی‌معنا (مثل UUID به‌جای نام)، و هر پاسخ طولانی‌تر از
نیاز، مستقیماً از همان فضای محدود کم می‌کند و شانس خطا را بالا می‌برد.
Anthropic می‌گوید: «Agentها فقط به‌اندازهٔ ابزاری که به آن‌ها می‌دهیم مؤثرند.»

## چند تکنیک مشخص

<Callout type="fact">
  **تجمیع ابزارها:** به‌جای سه ابزار جدا (`list_users`، `list_events`،
  `create_event`)، یک ابزار واحد و هدفمند مثل `schedule_event` بساز.
  **Namespace گذاری:** ابزارهای مرتبط را بر اساس سرویس/منبع گروه‌بندی کن
  (مثل `asana_search`، `jira_search`) تا شانس انتخاب اشتباه کم شود.
  **بازگرداندن Context قابل‌فهم:** به‌جای شناسهٔ فنی (UUID)، نام/فیلد
  قابل‌خوانش برگردان — این کار در آزمایش‌های Anthropic باعث کاهش Hallucination
  و بهبود دقت بازیابی شد. **پیغام خطای راهگشا:** به‌جای کد خطای مبهم یا
  Traceback، پیغام باید دقیقاً بگوید چه اصلاحی لازم است.
</Callout>

<Callout type="tip">
  اگر یک MCP Server یا هر Tool دیگری برای Agentهای خودتان می‌سازید: ابزار را
  مثل توضیح‌دادن یک کار به یک همکار تازه‌استخدام بنویسید (با Context ضمنی
  صریح‌شده)، اسم پارامترها را بدون ابهام انتخاب کنید (مثلاً `user_id` به‌جای
  `user`)، و پیش از هر چیز، Pagination/فیلتر/برش برای کنترل حجم پاسخ در نظر
  بگیرید — این موارد معمولاً اثر بزرگ‌تری از تغییر مدل دارند.
</Callout>
