## این موضوع چیست و چرا الان مطرح شده؟

وقتی یک Agent کدنویس مثل Claude Code یا Codex روی ماشین شما کد تولید‌شده
توسط مدل زبانی را اجرا می‌کند، دو خطر همیشه وجود دارد: یک اشتباه مدل که
باعث یک دستور مخرب شود، یا یک حملهٔ Prompt Injection که از طریق محتوای
یک فایل یا صفحهٔ وب، Agent را به اجرای کاری غیرمنتظره وادار کند. راه‌حل
رایج تا امروز معمولاً «Sandbox محلی» بوده — مثلاً یک Container یا VM
روی همان ماشین. سایمون ویلیسون، در پستی که در ۱۷ نوامبر ۲۰۲۶ منتشر کرد،
الگوی دیگری را معرفی می‌کند که آن را «Sandbox بیرونی» (External Sandbox)
می‌نامد: به‌جای اینکه خودِ Agent در یک محیط ایزوله اجرا شود، فقط *کدی که
Agent می‌خواهد اجرا کند* به یک سرویس جداگانه فرستاده می‌شود — خودِ Agent
و مدل زبانی بیرون از آن محیط باقی می‌مانند.

## چه زمانی این الگو به کارتان می‌آید؟

اگر یک Agent کدنویس (خودساخته یا یکی از ابزارهای موجود مثل Claude Code
یا Codex) می‌سازید که باید کد تولیدشده توسط مدل را روی ماشین کاربر یا
سرور اجرا کند، الگوی Sandbox بیرونی یک جایگزین قابل‌توجه برای Containerهای
محلی سنگین است: چون Agent و مدل بیرون از محیط ایزوله می‌مانند، می‌توانید
بین چند فناوری ایزوله‌سازی (WASM برای سبک‌ترین حالت، Apple Containers
برای مک، یا Quicksand/QEMU برای ایزولهٔ قوی‌تر) بدون تغییر در منطق خودِ
Agent جابه‌جا شوید. این الگو به‌خصوص برای تیم‌هایی که می‌خواهند چند سطح
اعتماد متفاوت (کد از منبع داخلی در برابر کد تولیدشده از یک Prompt خارجی
و بالقوه مخرب) را با سیاست‌های متفاوت دسترسی شبکه (از طریق همان Proxy
با Allow-list) مدیریت کنند، معنادار است.
