## چه مشکلی را حل می‌کند؟

تیم‌ها معمولاً همان کار تکراری را بار‌ها و بار‌ها به یک Agent توضیح
می‌دهند، و دانش نهادی تیم یا در لاگ‌های چت گم می‌شود یا فقط در ذهن یک نفر
باقی می‌ماند. Agent Skills برای همین ساخته شده‌اند: ثبت این دانش در فایل‌های
نسخه‌دار و قابل‌بازبینی. اما مقاله یک نکتهٔ مهم‌تر هم اضافه می‌کند: مرز
قابلیت‌حمل یک Skill کجاست؟ دستورالعمل‌های یک Skill می‌توانند بین Agentهای
مختلف منتقل شوند، اما ابزار، اعتبارنامه (Credentials)، Context پروژه و
مجوزها باید از محیط میزبان (Host) بیایند — نه از خود Skill. برای مثال، یک
Skill می‌تواند توضیح دهد *چگونه* باید از یک پایگاه‌داده پرس‌وجو کرد، اما
خودش دسترسی به آن پایگاه‌داده را نمی‌دهد.

<Callout type="fact" title="ساختار یک Skill">
  هر Skill یک پوشهٔ نسخه‌دار است با یک فایل `SKILL.md` در مرکز آن که
  Frontmatter آن نام و توضیح یک‌خطی Skill را مشخص می‌کند، و بدنهٔ آن می‌گوید
  Agent چه زمانی باید این Skill را فراخوانی کند و چه چیزی را بررسی/گزارش
  کند.
</Callout>

## نمونه‌های واقعی مقاله

مثال Data Forge نشان می‌دهد چگونه یک خط لولهٔ داده واحد به چند Skill
کوچک‌تر تقسیم می‌شود: `forge-init` جزئیات پروژه را کشف می‌کند، `forge-builder`
کل فرایند را تا رسیدن به یک Pull Request هماهنگ می‌کند، `forge-dbx` دسترسی
به پلتفرم داده را مدیریت می‌کند، و `forge-lint` استانداردهای تیم را اعمال
می‌کند. در یک مثال دیگر (پشتیبانی رویدادهای حادثه)، فرایند هفت فاز دارد که
هرکدام یک نقطهٔ تأیید انسانی دارند، و خروجی نهایی یک Pull Request شامل کد
خط لوله، تغییرات Schema و تست‌هاست.

## چه چیزی واقعیت است و چه چیزی توصیهٔ نویسنده؟

<Callout type="analysis" title="جداسازی توصیهٔ عملی از واقعیت فنی">
  ساختار فنی Skill (یک پوشهٔ نسخه‌دار با `SKILL.md`) و مثال‌های فرمت خروجی
  برای هر ابزار (Claude Code، Cursor، GitHub Copilot) واقعیت‌های مستند در
  مقاله‌اند. اما قواعد شش‌گانهٔ بالا — مثل «یک Skill باید یک کار با ورودی و
  خروجی مشخص انجام دهد» یا جملهٔ «self-verification is not verification» —
  توصیه و تجربهٔ شخصی نویسنده و همکارش از ساخت نمونه‌های Proof Agent و Data
  Forge هستند، نه یک استاندارد رسمی یا الزام فنی خودِ قالب Agent Skills.
  تیم‌های دیگر ممکن است به نتیجهٔ متفاوتی برسند.
</Callout>

## چه زمانی باید از Skill استفاده کرد، نه یک برنامهٔ کامل؟

طبق مقاله، Skillها برای کارهای تکراری و محدود که از قضاوت قابل‌استفادهٔ
مجدد سود می‌برند مناسب‌اند — مثل چک‌لیست‌ها، Releaseها، Migrationها یا خط
لولهٔ متریک. اما وقتی نیاز به یک رابط پایدار، وضعیت مشترک، ردپای Audit،
کنترل طولانی‌مدت یا مجوزهایی که باید خارج از مدل اعمال شوند دارید، بهتر است
یک برنامهٔ کامل بسازید، نه یک Skill. نکتهٔ عملی برای شروع: یک کاری را که از
توضیح‌دادن دوباره به Agent خسته شده‌اید انتخاب کنید، بنویسید چه چیزی لازم
دارد و کجا باید توقف کند و بازبین چه چیزی باید ببیند، سپس آن را با یک Agent
دیگر هم تست کنید.
