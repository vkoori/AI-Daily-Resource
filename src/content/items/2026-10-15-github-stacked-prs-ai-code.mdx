## مسئله: PR غول‌پیکر، بازبینی متوقف‌شده

وقتی یک Agent کدنویسی به‌تنهایی رها شود تا یک ویژگی کامل را پیاده‌سازی
کند، نتیجه رایج یک Pull Request با بیش از هزار خط تغییر است. در عمل، این
نوع PR عملاً بازبینی نمی‌شود: بازبین زمینه را در میانه خواندن از دست
می‌دهد، بازخورد سطحی می‌شود، و کیفیت کنترل کد افت می‌کند — دقیقاً برعکس
هدف بازبینی کد.

## راه‌حل: Stacked Pull Requests برای خروجی Agent

<Callout type="analysis">
  Stacked PRs تکنیکی شناخته‌شده در توسعه انسانی است؛ نکته این مقاله این
  است که همین تکنیک را عمداً برای خروجی Agent هم به کار می‌برد — نه فقط
  برای کار دستی توسعه‌دهنده.
</Callout>

## هشدار امنیتی مهم: دکمه Rebase وب را با احتیاط استفاده کنید

<Callout type="caution">
  دکمه «Rebase stack» در رابط وب GitHub، روی سرورهای GitHub اجرا می‌شود —
  یعنی Commitهای حاصل با کلید امضای شما امضا نمی‌شوند. اگر Branch
  Protection مخزن شما به Commit امضاشده نیاز دارد، باید به‌جای دکمه وب،
  دستور `gh stack rebase` را به‌صورت محلی اجرا کنید و سپس خودتان Push
  کنید.
</Callout>

## چطور یک Stack را بازبینی کنیم

<Callout type="tip">
  ترتیب پیشنهادی مقاله: ابتدا Stack را **از بالا به پایین** بخوانید تا
  زمینه کلی ویژگی را بگیرید، سپس بازبینی واقعی را **از پایین به بالا**
  انجام دهید — چون هر لایه بالاتر، منطقاً به لایه‌های زیرین خودش وابسته
  است. برای هر لایه یک چک‌لیست اختصاصی تعریف کنید؛ مثال‌های مقاله:
  اعتبارسنجی ورودی، پایداری قرارداد پاسخ (Response Contract)، مدیریت
  درست حالت خطا و حالت خالی، و این‌که آیا خروجی واقعاً به داده واقعی
  ردیابی می‌شود یا نه. مهم‌تر از همه: CI را روی **تک‌تک لایه‌ها** بررسی
  کنید، نه فقط روی بالاترین PR در Stack — یک لایه پایین‌تر شکسته می‌تواند
  زیر یک لایه بالاتر سبز، پنهان بماند.
</Callout>
