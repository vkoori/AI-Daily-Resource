## این موضوع چیست و چرا الان مطرح شده؟

با گسترش استفاده از چند ایجنت هم‌زمان برای یک وظیفه (مثلاً یک ایجنت
Triage می‌کند، ایجنت دیگر پیاده‌سازی می‌کند، ایجنت سوم بازبینی می‌کند)،
تیم‌های مهندسی زیادی با شکست‌های غیرمنتظره مواجه شده‌اند: خروجی یک
ایجنت در قالبی که ایجنت بعدی انتظارش را ندارد، واگذاری کار بدون مرز
مشخص، یا رفتار متفاوت در هر بار اجرا. این مقالهٔ GitHub Blog (هرچند
چند ماه پیش منتشر شده، اما هم‌چنان یکی از واضح‌ترین توضیح‌های موجود در
این حوزه است) استدلال می‌کند که دلیل اصلی این شکست‌ها معمولاً ضعف خودِ
مدل زبانی نیست، بلکه نبود ساختار مهندسی مشخص در تعامل بین ایجنت‌هاست —
یعنی باید با یک سیستم چند-ایجنتی مثل یک سیستم توزیع‌شده رفتار کرد، با
همان ریسک‌های حالت مشترک، ترتیب اجرا، و رفتار غیرقطعی.

## چه زمانی و برای چه کسی کاربرد دارد؟

این الگوها برای تیم‌هایی مفیدند که از یک ایجنت تکی به یک سیستم
چند-ایجنتی (حتی فقط دو یا سه ایجنت) حرکت می‌کنند و می‌خواهند از ابتدا
با معماری درست شروع کنند، نه بعد از دیدن اولین دسته شکست‌های عجیب. برای
تیم‌هایی که همین حالا از MCP برای اتصال ابزارها استفاده می‌کنند، این
پروتکل خودبه‌خود لایهٔ اعتبارسنجی مناسبی برای الگوی سوم فراهم می‌کند؛
برای تیم‌هایی که هنوز MCP ندارند، می‌توان همان ایده (اعتبارسنجی Schema
پیش از اجرا) را با ابزارهای ساده‌تر (مثل JSON Schema یا Pydantic) هم
پیاده‌سازی کرد.

## مقایسه با گزینه‌های مشابه

در برابر رویکردهای رایج‌تر مثل اعتماد به دستورالعمل‌های زبان طبیعی بین
ایجنت‌ها یا استفاده از یک Supervisor مرکزی که همه‌چیز را دوباره بررسی
می‌کند، رویکرد این مقاله غیرمتمرکزتر است: هر مرز بین ایجنت‌ها خودش
مسئول اعتبارسنجی قرارداد خودش است. این رویکرد پیچیدگی را از «حدس زدن از
روی لاگ» به «مشخص کردن اینکه کدام Schema نقض شده» منتقل می‌کند — که
برای Debugging ساده‌تر است، اما نیاز به سرمایه‌گذاری اولیهٔ بیشتر در
طراحی Schema و قراردادها دارد، که رویکردهای ساده‌تر (و شکننده‌تر) از
آن صرف‌نظر می‌کنند.
