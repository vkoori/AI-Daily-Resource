## این موضوع چیست و چرا الان مطرح شده؟

تا امروز، خودکارسازی کارهای مبتنی بر استدلال در یک مخزن — مثل triage
کردن Issueها، تحلیل علت شکست یک CI، به‌روزرسانی مستندات، یا نوشتن تست —
یا نیاز به اسکریپت‌نویسی دستی داشت یا به ابزارهای شخص ثالث خارج از
GitHub Actions متکی بود. **GitHub Agentic Workflows** (که با ابزار خط
فرمان `gh aw` ساخته و مدیریت می‌شود) این فاصله را با یک ایده ساده پر
می‌کند: به‌جای نوشتن YAML پیچیده، نویسنده یک فایل Markdown به زبان طبیعی
می‌نویسد که در آن هم شرایط اجرا (Trigger، سطح دسترسی) و هم دستورالعمل
ایجنت نوشته شده، و خودِ ابزار آن را به یک فایل Workflow استاندارد و
سخت‌شده (`.lock.yml`) ترجمه می‌کند. گیت‌هاب این پروژه را از پیش‌نمایش
عمومی خارج کرده و در ۲۸ اکتبر ۲۰۲۶ آن را به‌صورت عمومی (GA) روی
github.com برای پلن‌های Free، Team و Enterprise در دسترس قرار داده است.

## چه زمانی و برای چه کسی کاربرد دارد؟

این ابزار برای تیم‌هایی که همین حالا از GitHub Actions استفاده می‌کنند و
می‌خواهند وظایف تکراری اما نیازمند استدلال — نه صرفاً اجرای یک اسکریپت
ثابت — را خودکار کنند مناسب است: triage خودکار Issueها، خلاصه‌سازی
شکست‌های CI، به‌روزرسانی مستندات هم‌زمان با تغییر کد، یا بازبینی اولیهٔ
PR. چون موتور قابل انتخاب است (Copilot، Claude، Codex، Gemini)، تیم‌هایی
که از قبل روی یکی از این مدل‌ها License دارند می‌توانند بدون تغییر
Provider از همان استفاده کنند. مدل مجوز محدود (فقط-خواندنی پیش‌فرض +
safe-outputs) آن را برای مخازن حساس‌تر هم قابل‌استفاده‌تر می‌کند، اما
سربار مدیریتی (تنظیم Secret برای هر موتور، سیاست‌های Org، سقف هزینه)
برای تیم‌های کوچک ممکن است قابل‌توجه باشد.

## مقایسه با گزینه‌های مشابه

بر خلاف اسکریپت‌نویسی مستقیم YAML برای Actions یا استفاده از یک CLI
ایجنتی عمومی (مثل Claude Code یا Codex CLI) به‌صورت مستقل از Actions،
این پروژه ایجنت را درون همان مدل اجرای Actions — با همان Runnerها،
سیاست‌های سازمانی، و گزارش‌دهی — نگه می‌دارد و مرز اعتماد (Trust
Boundary) را با یک لایهٔ اعلامی (Frontmatter + safe-outputs) به‌جای کد
دلخواه تعریف می‌کند. هزینهٔ این رویکرد، وابستگی به اکوسیستم GitHub
Actions و پیچیدگی تنظیم اولیه (Authentication هر موتور، سیاست‌های
Copilot CLI برای صورت‌حساب سازمانی) است؛ صفحهٔ رسمی هیچ مقایسهٔ عددی با
جایگزین‌های دیگر ارائه نکرده، پس قضاوت دربارهٔ برتری واقعی این رویکرد
باید از تجربهٔ عملی تیم‌ها به‌دست بیاید.
